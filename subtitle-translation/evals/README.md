# Agent evaluations

These cases test agent behavior, not just the Python helper. The repository does
not include measured model-quality benchmark results.

## Cases

[evals.json](evals.json) contains four task specifications and separate activation
checks:

| Case | Main checks |
| --- | --- |
| Continuity SRT → Russian | Glossary inflection, homonyms, ambiguity, numbers, and batch boundaries |
| Protected WebVTT → Spanish | Metadata/tags, speaker turns, and instruction-like dialogue |
| Malformed SRT → French | Stop on invalid timing without modifying the source or publishing a final file |
| Read-only Russian terminology review | Detect deliberately inconsistent names/places without modifying files; accept valid inflection |

The review fixture deliberately includes terminology drift and is not a gold
translation. Its cue 2 also loses information about who gave the key; a broader
semantic review should catch that, but the task assertions focus on terminology.

Run activation checks separately: they test skill selection, including indirect
requests, missing inputs, and unrelated tasks. Unsupported ASS input should
activate the subtitle workflow only to explain its boundary, not silently convert.

## Run a paired comparison

1. Record the repository revision, host/version, model, settings, permissions,
   and which other skills are enabled. Run helper tests first:

   ```bash
   python3 -m unittest discover -s tests -v
   ```

2. Create two isolated workspaces per case **outside the installed skill**. Copy
   fixtures into each workspace under `evals/files/` so the prompts' relative
   paths resolve. Keep original fixture bytes unchanged.
3. Start a fresh agent session for each run. In the **with-skill** configuration,
   expose this skill normally. In the **without-skill** configuration, ensure the
   agent cannot discover/read this skill or its references/scripts. Use the same
   model, settings, fixture bytes, and case prompt in both configurations.
   Do not expose previous outputs, grades, or transcripts to either run.
4. Use each task's `prompt` unchanged. Do not force explicit skill invocation when
   measuring automatic activation. If testing explicit invocation, record it as
   a separate configuration.
5. Save all produced files, the execution transcript, elapsed time, and actual
   token usage if available. Record unavailable measurements as unavailable,
   never as zero. Repeat each configuration in fresh sessions when feasible.
6. Grade outputs with the assertions in `evals.json`, then inspect successful
   **and** failed traces. Record blockers and tool/permission failures separately
   from mistranslations.

Suggested layout (not generated by a bundled runner):

```text
subtitle-translation-workspace/iteration-1/
  continuity/
    with-skill/run-1/       # fixtures, outputs, transcript, run metadata, grades
    without-skill/run-1/
  protected/
  malformed/
  summary.json
```

## Grade with evidence

Use code for mechanical checks. From the repository root, run the helper against
both configurations' resulting files; the evaluator may use the helper even
though the baseline agent must not have access to it:

```bash
python3 subtitle-translation/scripts/subtitle_guard.py verify /absolute/path/to/source.srt /absolute/path/to/translated.srt
```

Use `.vtt` paths for the WebVTT case. Also compare source hashes before/after and
inspect missing outputs in the malformed case. A missing final translation is
expected for malformed input, not a translation-quality failure.

A bilingual reviewer should compare all source/target cue pairs for fidelity,
terminology, ambiguity, and omissions. Structural PASS is not semantic PASS.
For each assertion record `passed` and specific evidence (cue IDs, quoted text,
file paths, command results). Mark ungradable assertions explicitly rather than
assuming success. Keep mechanical, semantic, and routing results separate.

Example grade record:

```json
{
  "assertion": "Rose the person and the flower remain distinct",
  "passed": true,
  "evidence": "Quote the actual target text and cue IDs here."
}
```

This is a format example, not an observed result. Review full outputs in addition
to assertions; a checklist can miss errors it was not designed to catch.

## Long-job and recovery experiments

These are manual protocols, not claimed results or an automated runner. Use a
rights-cleared full episode/movie for quality evaluation; repeated synthetic
cues can test plumbing but not narrative continuity.

- **Long file:** run the same file/model/settings on the previous revision and
  current revision. Record total input/output/cache tokens (if exposed), retries,
  tool calls, truncations, completed cues, and elapsed time. Grade full semantic
  fidelity, distant callbacks, names, and batch boundaries. Do not count smaller
  SKILL.md size as measured per-job savings.
- **Resume:** interrupt after two accepted parts. Start a fresh session with only
  the source and saved workspace; ask to continue. Assert no accepted cue is
  regenerated unnecessarily, every remaining cue is present, and final verify
  succeeds. Separately change source bytes and assert stale hashes are rejected.
- **Glossary change:** after an accepted part, revise an approved spelling. Ask to
  continue with the revision. Assert every affected earlier occurrence is reviewed,
  unaffected files stay unchanged, and the checkpoint records the new revision.
- **Truncation:** constrain output or use dense batches. Assert failed work is not
  marked accepted, attempts are bounded, smaller ranges retain neighboring context,
  and merge excludes abandoned parts. Never truncate successful output and present
  it as an observed model failure.
- **Small model:** repeat on an intended smaller model as well as a capable one.
  Report adherence failures separately from mistranslation. No universal weak-model
  guarantee follows from passing one language pair.

## Iterate

- Compare raw pass counts per case/configuration; report sample sizes and failures.
- With repeated runs, summarize variation, elapsed time, and token cost as well
  as pass rates. Do not infer statistical reliability from one run.
- Blind the output labels during semantic comparison where practical.
- Inspect false activations, missed activations, wasted steps, and repair loops.
- Revise the smallest general instruction that addresses an observed failure,
  then rerun all cases in a new iteration directory.
- Add real failure cases, including long files, glossary conflicts, review-only
  requests, resumption, and additional language pairs. Keep some cases held out
  to check that changes generalize.

Methodology: [Evaluating skill output quality](https://agentskills.io/skill-creation/evaluating-skills).
